> **같은 시간, 같은 손, 다른 시작점.**

>지난 모임에서 물었습니다.
> `/goal` 한 방 vs `/plan` 잡고 가기 —
> 무엇이 더 '바이브'인가, 무엇이 더 결과로 남는가.

이번엔 한 걸음 더 갑니다.

완성도 자랑 대회가 아닙니다. 서로 배워나아고 공부하고 지식을 다소  공유하는 스파르타식(?!) 과정입니다.

**흐름(flow), 실험, 워크플로 비교**가 본게임입니다.

`/plan`으로 손대기 전에 설계를 고정할 것인가, `/goal` 한 줄로 증명 가능한 끝만 두고 뛸 것인가.

## 주제 -AI에 대한 저항

어떻게 하면 AI 슬롭을 만들지 않고 창작자 본인이 주체가 되어 게임의 창작 주권,제어권을 유지할 수 있을까요?

### "우리는 왜, 그리고 어떻게 시작하는가?"

를 같은 시계 아래에서 비교하는 실험입니다.

스터디잼에 오셔서 무엇이든 만드셔도 됩니다.
게임, 툴, 자동화, 웹, 봇, 쓸모없는 장난감 — 전부 OK.
---

## 🎯 왜 이 테마인가?

- AI가 개발 과정 한가운데 들어옴
- 프로토타입 속도가 극단적으로 빨라짐
- 기획·디자인·개발 경계가 흐려짐
- 그런데 **시작 방식(goal/plan/스펙 덤프)** 에 따라 당일 결과가 갈림
- "바이브"만 외치면 놀이가 되고, "계획만" 외치면 몸이 굳음

지난 모임이 **바이브의 정의**를 몸으로 더듬는 자리였다면,
이번엔 **바이브의 시작 프로토콜**을 겨뤄 보는 자리입니다.

막연히 "재미있게 만들어"라고 던지는 방식은 이미 한계가 드러났습니다.
며칠 만에 프로토타입은 나와도, 설계를 다시 고정한 뒤에야 정식까지 간 경우가 많습니다.
그걸 두고 바이브 코딩에서 바이브 엔지니어링으로의 전환이라고 부르기도 합니다.

요즘 잘 되는 루프는 이겁니다.

`/init`로 규칙 고정 → `/plan`으로 손대기 전에 설계 → 검증 가능한 `/goal`로 자율 루프 → 스킬로 에셋·구현·플레이 검증 → `/review`로 닫기.

## 🏁 트랙 (택 1)

### A. `/goal` 트랙

- 시작 시 **goal 1개만** 확정 (최대 500자)
- 사전 초대형 스펙/md 투입 금지
- 진행 중 추가는 대화 로그·커밋·메모로만

### B. `/plan` 트랙

- 시작 전 `plan.md` 허용
  - **최대 200줄** 또는 **8,000자** (먼저 닿는 쪽)
- plan 밖 숨은 천 줄 스펙 금지
- plan 변경 시 **변경 이유 3줄 이내**

> 핵심: "프롬프트 한 줄" 쇼가 아님.
> **상한 있는 시작 조건**에서 누가 더 멀리 가는지.

## 게임 개발에서 쓰는 명령

바이브 코딩에서 게임 개발에 공통으로 쓰는 명령은 크게 세 층입니다.
**빌트인 세션 제어**(`/plan`, `/goal`), **스킬로 만든 재사용 절차**, **게임 페이즈용 커스텀 명령**입니다.
Claude Code와 Codex CLI/앱이 이 세 층을 거의 같은 이름으로 맞췄고, 인디·웹게임 쪽 실전 패턴도 여기로 모입니다.

이번 잼에서 `/plan` 트랙과 `/goal` 트랙은 바로 이 차이를 겨룹니다.

### 1. 세 도구가 공유하는 축

| 명령 | Claude Code | Codex CLI/앱 | 게임에서의 역할 |
| --- | --- | --- | --- |
| `/plan` | Plan Mode. 읽기 전용, 승인 전 수정 금지. Shift+Tab으로도 전환 | Plan Mode. 실행 전에 단계 계획만 제시 | 코어 루프, 씬 구조, 데이터 모델을 코드 전에 잠금 |
| `/goal` | 완료 조건이 성립할 때까지 턴을 이어 감 | set / pause / resume / clear | "플레이 가능한 1판" 같은 증명 가능한 종료 조건 |
| `/skills` | `.claude/skills/*/SKILL.md`가 `/이름`이 됨 | `/skills`로 로컬 스킬 주입 | 에셋 생성, 웹게임 테스트, 엔진별 구현 절차 |

`/plan`은 **어떻게**를 고정하고, `/goal`은 **언제 멈출지**를 고정합니다.
둘을 빼면 에이전트가 범위 밖으로 계속 덧붙입니다.

`/goal`에 넣는 문장은 감정("재미있게")이 아니라 관찰 가능해야 합니다.

```text
/goal game.html opens in browser, plays a complete Catan match vs 3 AI bots,
declares the winning house at 10 VP, zero console errors during full play,
stop after 60 turns
```

한 줄 `/goal`로 짧은 시간에 추출 슈터를 뽑은 데모도 같은 패턴입니다.
그 전에 이미지 생성 스킬을 켜고, Plan 모드로 모호한 부분을 지운 다음 자율 루프에 넘깁니다.

### 2. 세션을 망치지 않는 공통 빌트인

게임 세션은 컨텍스트가 빨리 찹니다.
스프라이트 설명, 로그, 긴 diff가 쌓이면 후반 코드가 무너집니다.

**시작·기억**

- `/init` — 프로젝트 지침 뼈대 생성. Claude는 `CLAUDE.md`, Codex는 `AGENTS.md`. 엔진, 해상도, 입력, "하지 말 것"을 여기 고정.
- `/memory` — 세션을 넘어 유지할 결정만 기록. 밸런스 숫자, 아트 바이블 한 줄, 금지 패턴.

**계획·실행·되돌리기**

- `/plan [설명]` — 구현 전 계획. 승인 전에는 파일을 안 건드림.
- `/goal [조건]` / `/goal pause` / `/goal resume` / `/goal clear` — 장기 목표. 긴 스펙은 파일로 빼고 조건만 한 줄로.
- `/diff` — 이번 세션이 실제로 바꾼 것.
- `/rewind` — 대화와 코드를 체크포인트로 되돌림. 실험 분기가 많을 때.
- `/fork` — 현재 대화를 복제해 다른 접근을 시험.
- `/review` — 워킹트리 리뷰. 동작 변화와 빠진 테스트.

**컨텍스트·비용**

- `/compact [지시]` — 오래된 턴을 요약해 창을 비움. "코어 루프와 입력 매핑은 유지"처럼 남길 것을 지정.
- `/clear` — 하드 리셋. 기능 하나가 끝난 뒤 새 스토리로 넘어갈 때.
- `/context` — 토큰이 어디에 쓰이는지.
- `/usage` — 세션 비용. `/goal` 루프는 토큰을 많이 태우므로 턴 상한을 같이 거는 편이 안전합니다.
- `/btw` 또는 `/side` — 본 작업을 끊지 않는 옆 질문.

**모델·권한·도구**

- `/model` — 계획은 추론이 센 모델, 자잘한 수정은 빠른 모델.
- `/fast` — 빠른 티어.
- `/permissions` — 승인 정책. 에셋 생성·브라우저 테스트까지 맡길 때만 완화.
- `/mcp` — Godot, Blender, Playwright, GitHub 연결 상태.
- `/agent` — 서브에이전트 스레드 전환. 아트 / 로직 / QA를 나눴을 때.
- `/resume` — 어제 세션 이어하기.

### 3. 게임 페이즈별 커스텀 명령

인디가 복붙해 쓰는 묶음에는 Godot 4 / Unity / Unreal 5를 전제로 한 스튜디오 명령이 있습니다.
웹 인디(PixiJS, Phaser, Vite)는 이 중 기획·스토리·QA만 가져와 스킬로 두면 됩니다.

**온보딩**

- `/start` — 지금 단계(아이디어 / 콘셉트 / 기존 코드)를 묻고 `project.yaml`을 씀.
- `/setup-engine` — 엔진과 버전. 예: `/setup-engine godot 4`.
- `/project-stage-detect` — 빠진 문서·시스템 감사.
- `/adopt` — 이미 있는 GDD를 이 구조로 이관.
- `/help` — 현재 단계에서 다음에 칠 명령.

**기획 (코드 전에 여기서 끝내는 편이 이득)**

- `/brainstorm` — 콘셉트를 좁힘.
- `/map-systems` — 시스템을 나누고 의존 순서를 정함. 이동 → 충돌 → 인벤토리 순서.
- `/design-system` — 시스템 하나 GDD. 코어 루프는 여기.
- `/quick-design` — 수치 튜닝, 작은 추가.
- `/review-all-gdds` — 문서끼리 모순.
- `/propagate-design-change` — GDD를 고치면 영향 받는 문서를 표시.

**아트·UX**

- `/art-bible` — 팔레트, 실루엣, 픽셀 크기, 금지 스타일.
- `/asset-spec` — 스프라이트 규격(프레임 수, 피벗, 시트 크기).
- `/asset-audit` — 스펙 대비 빠진 에셋.
- `/ux-design`, `/ux-review` — HUD, 실패 화면, 일시정지.

**구조**

- `/create-architecture` — 씬/엔티티/이벤트 경계.
- `/architecture-decision` — ADR 한 장.
- `/create-control-manifest` — 입력 표. 키보드/터치/게임패드.

**구현 루프**

- `/create-epics` — 시스템 단위. "대시", "웨이브", "게임오버".
- `/create-stories` — 수용 기준이 있는 구현 단위.
- `/story-readiness` — READY / NEEDS WORK / BLOCKED.
- `/dev-story` — 스토리 하나를 구현.
- `/story-done` — 구현·테스트·리뷰 후 닫기.
- `/sprint-plan`, `/sprint-status`.

**리뷰·밸런스**

- `/code-review`, `/design-review`.
- `/balance-check` — 클리어 시간, DPS, 드랍 곡선.
- `/scope-check` — 이번 빌드 밖을 잘라 냄.
- `/perf-profile` — 드로우콜, GC, 모바일 프레임.

**QA·출시**

- `/qa-plan`, `/smoke-check` — 기동과 크리티컬 패스.
- `/soak-test` — 장시간 플레이.
- `/prototype`, `/vertical-slice` — 세로 조각. 잼·데모용으로 가장 자주 씀.
- `/playtest-report`, `/bug-report`.
- `/release-checklist`, `/changelog`.

추천 일상 루프는 이렇습니다.

```text
/sprint-plan → /create-stories
→ /story-readiness → /dev-story → /code-review → /story-done
→ /sprint-status
```

잼이나 짧은 프로토타입이면 `/brainstorm` → `/vertical-slice` → `/smoke-check`만으로도 충분합니다.

### 4. 웹·인디에 붙는 스킬

권하는 조합은 **Plan → 브라우저 구현 → 이미지 생성 → 브라우저로 직접 플레이**입니다.
루프는 `구현 → 입력 → 일시정지 → 상태 관찰 → 조정`이고, 관찰용 훅을 남깁니다.
스크린샷만 보고 "되는 것 같다"고 끝내지 않습니다.

같이 켜 두는 것:

- **imagegen** — 컨셉, 스프라이트, 배경, UI. 프롬프트는 재사용할 수 있게 파일로 남김.
- **develop-web-game** — 로컬 서버의 게임을 실제로 조작.
- **플레이 검증** — 타이밍, 히트감, HUD를 라이브 빌드에서 수정.

웹 인디에서 자주 만드는 커스텀 명령:

| 명령 | 하는 일 |
| --- | --- |
| `/loop` | 입력→판정→보상→재시작만. 메타, 스토리, 상점 금지 |
| `/feel` | 히트스톱, 카메라 쉐이크, 화면 플래시, SFX 훅만 조정 |
| `/sprite` | 아트 바이블 규격으로 시트 생성 후 피벗·프레임 검증 |
| `/balance` | 지정 시뮬 N회, 클리어율·평균 시간만 보고 |
| `/mobile` | 터치 타깃, 세이프 에어리어, 60fps 예산 |
| `/itch` | 빌드, 스크린샷, 설명문, 조작 안내 |
| `/jam` | 짧은 스코프. 기능 상한, 아웃 오브 스코프 명시 |

Godot면 씬·노드를 읽게 하고, 그 다음에 `/vertical-slice`를 넘기는 흐름이 표준에 가깝습니다.
엔진 코드를 채팅창에 붙여 넣는 방식은 거의 쓰지 않습니다.

### 5. 실제로 치는 순서

**새 프로토타입 (웹, 하루~이틀)**

1. `/init` — 스택, 해상도, "싱글 파일 또는 src/ 3개 이하".
2. `/plan` — 코어 루프 한 문장, 화면 3개, 안 만들 것.
3. 계획을 `PLAN.md`로 저장. 승인 후에만 구현.
4. 이미지 생성으로 플레이어·적·타일만.
5. `/goal` — "로컬에서 시작 버튼을 누르면 30초 생존 후 게임오버가 뜨고, 콘솔 에러 0, 40턴에서 중단".
6. `/review` → `/compact`.

**이미 있는 빌드에 기능 하나**

1. `/plan 대시 추가. 쿨다운 0.8초, 무적 없음, 모바일 스와이프`.
2. `/dev-story` 또는 스토리 파일 하나.
3. `/goal` — 대시 중 충돌이 기존 히트 판정과 이중으로 안 들어가고, 기존 웨이브 테스트가 통과.
4. `/balance-check` 또는 `/feel`.
5. `/story-done`.

**막힐 때**

- 범위가 새면 `/scope-check`.
- 손이 안 맞으면 `/feel`만 분리. 로직 리팩터와 섞지 않음.
- 컨텍스트가 꼬이면 `/compact` 후 `/clear`, `PLAN.md`만 다시 읽힘.
- 실험이 실패하면 `/rewind` 또는 `/fork`.

### 6. `/goal`을 깨지지 않게 쓰는 조건

1. Brief — 한두 문장.
2. Stack — 엔진, 라이브러리, 스킬.
3. Scope — 비주얼 / 기능.
4. Out of Scope — 이게 없으면 루프가 상점을 만들기 시작합니다.
5. Constraints — 유지할 것(기존 입력, 60fps, 파일 수).
6. Definition of Done — 검증 문장 하나.
7. Acceptance — 5~10개 하위 체크.
8. Verification — 매 턴 돌릴 명령 또는 눈으로 볼 조건.
9. Turn Budget — 상한. 없으면 토큰만 탑니다.

나쁜 예: `/goal 재밌는 로그라이크 완성`.
나은 예: `/goal npm run dev 후 3웨이브 클리어, 게임오버에서 재시작, 콘솔 에러 0, 25턴에서 중단`.

명령 이름을 외우기보다, **계획(`/plan`)과 종료 조건(`/goal`)을 코드보다 먼저 파일로 남기는 것**이 이번 주제의 공통 규율입니다.
스킬은 그 다음, 반복되는 손(시트 규격, 플레이 테스트, 스토리 닫기)을 `/` 하나로 줄이는 용도입니다.
