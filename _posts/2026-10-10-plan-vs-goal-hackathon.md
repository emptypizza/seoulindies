## 이번엔 뭘 겨룰까요?

지난 모임에서 물었습니다.
**「AI 슬롭인 바이브 코딩이 아닙니다. 에이전틱 코딩이란 무엇입니까?」**

이번엔 한 걸음 더 갑니다.

완성도 자랑 대회가 아닙니다.
서로 배워 나가고, 공부하고, 지식을 나누는 과정입니다.

**흐름(flow), 실험, 워크플로 비교**가 본게임입니다.

`/plan`으로 손대기 전에 설계를 고정할 것인가, `/goal` 한 줄로 증명 가능한 끝만 두고 뛸 것인가.
어느 쪽이든 결정권은 창작자에게 있습니다. 에이전트가 많이 썼다는 사실이 작품의 주인이 바뀌었다는 뜻은 아닙니다.

## 주제 — AI 슬롭에 대한 저항

어떻게 하면 AI 슬롭을 만들지 않고, 창작자 본인이 주체가 되어 게임의 창작 주권과 제어권을 유지할 수 있을까요?

### "우리는 왜, 그리고 어떻게 시작하는가?"

를 같은 시계 아래에서 비교하는 실험입니다.

스터디잼에 오셔서 무엇이든 만드셔도 됩니다.
게임, 툴, 자동화, 웹, 봇, 쓸모없는 장난감 — 전부 OK.
다만 나온 결과를 그대로 받는 자리는 아닙니다.
시킨 일, 버린 일, 직접 고친 일을 말할 수 있어야 합니다.

---

## 🎯 왜 이 테마인가?

- AI가 개발 과정 한가운데 들어옴
- 프로토타입 속도가 극단적으로 빨라짐
- 기획·디자인·개발 경계가 흐려짐
- 그런데 **시작 방식(goal/plan/스펙 덤프)** 에 따라, 창작자가 남는지 슬롭만 남는지가 갈림
- "바이브"만 외치면 놀이가 되고, "계획만" 외치면 몸이 굳음
- 빨리 나온 화면을 창작으로 착각하면 제어권을 잃음

지난 모임이 **바이브의 정의**를 몸으로 더듬는 자리였다면,
이번엔 **창작자가 주도권을 잃지 않는 시작 프로토콜**을 겨뤄 보는 자리입니다.

막연히 "재미있게 만들어"라고 던지면 에이전트는 범위 밖으로 계속 덧붙입니다.
며칠 만에 프로토타입은 나와도, 설계를 다시 잠그고 사람이 승인한 뒤에야 작품이 됩니다.

저항은 도구를 거부하는 일이 아닙니다.
규칙을 먼저 고정하고, 계획을 승인하기 전에는 파일을 열지 않고, 끝나는 조건을 관찰 가능한 문장으로 적고, 결과를 리뷰한 뒤에만 받는 일입니다.

`/init`로 하지 말 것을 적기 → `/plan`으로 손대기 전에 설계를 잠그기 → `/goal`은 감정 대신 검증 문장 → 스킬은 반복 손만 맡기기 → `/review`로 창작자가 닫기.

## 🏁 초반에 공개하는 것

이번 잼의 초반은 트랙 선택이 아닙니다.
**게임 개발 구현 계획을 투명하게 공개**합니다.
무엇을 만들고, 어떤 순서로 손을 대며, 어디까지가 이번 범위인지 참가자끼리 볼 수 있게 꺼냅니다.
숨긴 스펙으로 시작하지 않습니다.

아래 `/goal`, `/plan` 구분은 그 계획을 적는 **예시**입니다.
둘 중 하나를 골라 겨루는 규칙이 아닙니다.

### 예시 A. `/goal`처럼 적기

- 시작 시 **goal 1개만** 확정 (최대 500자)
- 그 문장은 "재미있게"가 아니라, 끝나면 눈으로 확인할 수 있는 조건
- 사전 초대형 스펙/md 투입 금지
- 진행 중 추가는 대화 로그·커밋·메모로만
- goal 밖을 에이전트가 만들면, 그건 성과가 아니라 범위 이탈

### 예시 B. `/plan`처럼 적기

- 시작 전 `plan.md` 허용
  - **최대 200줄** 또는 **8,000자** (먼저 닿는 쪽)
- plan 밖 숨은 천 줄 스펙 금지
- plan 변경 시 **변경 이유 3줄 이내**
- 승인 전에는 구현 파일을 고치지 않음

> 핵심은 어느 예시로 적든, 초반 구현 계획이 공개되어 있다는 점입니다.
> "프롬프트 한 줄" 뒤에 계획을 숨기지 않습니다.

---

## 🔥 핵심 방향

1. **주권은 창작자에게.** 에이전트 환경(Cursor / VSCode+AI / Claude / Codex / Hermes / 로컬 LLM…)은 손이되, 채택과 폐기는 사람이 한다.
2. **과정까지 공유.** 막힌 점, 버린 것, 직접 고친 것, 먹힌 지시와 거부한 지시.

## 게임 개발에서 쓰는 명령

명령을 많이 아는 것이 이 잼의 점수가 아닙니다.
명령은 창작자가 세션의 주도권을 빼앗기지 않으려고 쓰는 경계입니다.

쓰는 층은 세 가지입니다.
**빌트인 세션 제어**(`/plan`, `/goal`), **스킬로 만든 재사용 절차**, **게임 페이즈용 커스텀 명령**.
이름은 도구마다 비슷합니다. 의미는 하나입니다. 에이전트가 멋대로 이어 가지 못하게 막는 일.

### 1. 세 도구가 공유하는 축

| 명령 | Claude Code | Codex CLI/앱 | 창작자가 지키는 것 |
| --- | --- | --- | --- |
| `/plan` | Plan Mode. 읽기 전용, 승인 전 수정 금지. Shift+Tab으로도 전환 | Plan Mode. 실행 전에 단계 계획만 제시 | 코어 루프, 씬 구조, 데이터 모델을 코드 전에 잠금 |
| `/goal` | 완료 조건이 성립할 때까지 턴을 이어 감 | set / pause / resume / clear | "플레이 가능한 1판"처럼 증명 가능한 종료. 감정 문장은 금지 |
| `/skills` | `.claude/skills/*/SKILL.md`가 `/이름`이 됨 | `/skills`로 로컬 스킬 주입 | 반복되는 손만 맡김. 취향과 폐기 판단은 맡기지 않음 |

`/plan`은 **어떻게**를 고정하고, `/goal`은 **언제 멈출지**를 고정합니다.
둘을 빼면 에이전트가 범위 밖으로 계속 덧붙이고, 그 결과가 슬롭이 됩니다.

`/goal`에 넣는 문장은 감정("재미있게")이 아니라 관찰 가능해야 합니다.
관찰할 수 있어야 창작자가 받고 거절할 수 있습니다.

```text
/goal game.html opens in browser, plays a complete Catan match vs 3 AI bots,
declares the winning house at 10 VP, zero console errors during full play,
stop after 60 turns
```

한 줄로 끝내는 데모도 같은 패턴입니다.
이미지 생성은 필요한 조각만 시키고, Plan으로 모호한 부분을 지운 다음, 자율 루프에 넘깁니다.
루프가 끝난 뒤 받는 사람은 여전히 창작자입니다.

### 2. 세션을 창작자에게 되돌리는 빌트인

게임 세션은 컨텍스트가 빨리 찹니다.
스프라이트 설명, 로그, 긴 diff가 쌓이면 후반에는 시킨 적 없는 기능이 들어옵니다.
아래 명령은 그 흐름을 끊습니다.

**시작·기억**

- `/init` — 프로젝트 지침 뼈대. Claude는 `CLAUDE.md`, Codex는 `AGENTS.md`. 엔진, 해상도, 입력, "하지 말 것"을 여기 고정.
- `/memory` — 세션을 넘어 유지할 결정만. 밸런스 숫자, 아트 바이블 한 줄, 금지 패턴. 에이전트의 장광설은 기억하지 않음.

**계획·실행·되돌리기**

- `/plan [설명]` — 구현 전 계획. 승인 전에는 파일을 안 건드림.
- `/goal [조건]` / `/goal pause` / `/goal resume` / `/goal clear` — 장기 목표. 긴 스펙은 파일로 빼고 조건만 한 줄로. 조건이 충족되면 멈춤.
- `/diff` — 이번 세션이 실제로 바꾼 것. 설명과 다르면 받지 않음.
- `/rewind` — 대화와 코드를 체크포인트로 되돌림. 실험이 슬롭이 되면 버림.
- `/fork` — 현재 대화를 복제해 다른 접근을 시험. 본류를 오염시키지 않음.
- `/review` — 워킹트리 리뷰. 동작 변화와 빠진 테스트. 창작자가 닫기 전에 봄.

**컨텍스트·비용**

- `/compact [지시]` — 오래된 턴을 요약. "코어 루프와 입력 매핑은 유지, 버려진 실험은 삭제"처럼 남길 것을 지정.
- `/clear` — 하드 리셋. 기능 하나가 끝난 뒤 새 일로 넘어갈 때. 이전 슬롭을 다음 기능에 붙이지 않음.
- `/context` — 토큰이 어디에 쓰이는지.
- `/usage` — 세션 비용. `/goal` 루프는 토큰을 많이 태우므로 턴 상한을 같이 겁니다.
- `/btw` 또는 `/side` — 본 작업을 끊지 않는 옆 질문. 본 구현을 산만하게 만들지 않음.

**모델·권한·도구**

- `/model` — 계획은 추론이 센 모델, 자잘한 수정은 빠른 모델. 모델이 바뀌어도 승인 주체는 사람.
- `/fast` — 빠른 티어. 속도가 검토를 대체하지 않음.
- `/permissions` — 승인 정책. 에셋 생성과 브라우저 테스트까지 맡길 때만 완화. 기본은 승인.
- `/mcp` — Godot, Blender, Playwright, GitHub 연결 상태. 연결됐다고 씬을 마음대로 고치게 두지 않음.
- `/agent` — 서브에이전트 전환. 아트 / 로직 / QA를 나눠도, 합치는 판단은 창작자.
- `/resume` — 어제 세션 이어하기. 이어 받기 전에 어제 버린 것을 확인.

### 3. 게임 페이즈별 커스텀 명령

스튜디오용 명령 묶음은 Godot 4 / Unity / Unreal 5를 전제로 한 것이 많습니다.
웹 인디(PixiJS, Phaser, Vite)는 기획·스토리·QA만 가져와 스킬로 두면 됩니다.
가져오는 이유는 생산량 자랑이 아니라, 단계마다 사람이 서명할 자리를 만들기 위해서입니다.

**온보딩**

- `/start` — 지금 단계(아이디어 / 콘셉트 / 기존 코드)를 묻고 `project.yaml`을 씀.
- `/setup-engine` — 엔진과 버전. 예: `/setup-engine godot 4`.
- `/project-stage-detect` — 빠진 문서·시스템 감사.
- `/adopt` — 이미 있는 GDD를 이 구조로 이관. 없는 설정을 지어내지 않음.
- `/help` — 현재 단계에서 다음에 칠 명령.

**기획 (코드 전에 여기서 끝내는 편이 이득)**

- `/brainstorm` — 콘셉트를 좁힘. 넓히지 않음.
- `/map-systems` — 시스템을 나누고 의존 순서를 정함. 이동 → 충돌 → 인벤토리.
- `/design-system` — 시스템 하나. 코어 루프는 여기. 창작자가 문장을 고친 뒤에만 구현.
- `/quick-design` — 수치 튜닝, 작은 추가. 풀 설계가 과한 변경용.
- `/review-all-gdds` — 문서끼리 모순. 에이전트가 메운 구멍을 찾음.
- `/propagate-design-change` — 설계를 고치면 영향 받는 문서를 표시. 조용히 따라 고치지 않음.

**아트·UX**

- `/art-bible` — 팔레트, 실루엣, 픽셀 크기, 금지 스타일. 이미지 생성이 매번 흔들리지 않게 하는 앵커.
- `/asset-spec` — 스프라이트 규격(프레임 수, 피벗, 시트 크기).
- `/asset-audit` — 스펙 대비 빠진 에셋. 스펙 밖 에셋은 슬롭.
- `/ux-design`, `/ux-review` — HUD, 실패 화면, 일시정지. 플레이어가 보는 화면은 창작자가 승인.

**구조**

- `/create-architecture` — 씬/엔티티/이벤트 경계.
- `/architecture-decision` — 결정 한 장. "이 엔진, 저 엔진 아님"처럼 거절을 남김.
- `/create-control-manifest` — 입력 표. 키보드/터치/게임패드.

**구현 루프**

- `/create-epics` — 시스템 단위. "대시", "웨이브", "게임오버".
- `/create-stories` — 수용 기준이 있는 구현 단위. 기준 없는 스토리는 시작하지 않음.
- `/story-readiness` — READY / NEEDS WORK / BLOCKED.
- `/dev-story` — 스토리 하나를 구현. 옆 스토리로 새지 않음.
- `/story-done` — 구현·테스트·리뷰 후 창작자가 닫기.
- `/sprint-plan`, `/sprint-status`.

**리뷰·밸런스**

- `/code-review`, `/design-review`.
- `/balance-check` — 클리어 시간, DPS, 드랍 곡선. 숫자가 취향을 대신하지 않음.
- `/scope-check` — 이번 빌드 밖을 잘라 냄. 저항의 실무 명령.
- `/perf-profile` — 드로우콜, GC, 모바일 프레임.

**QA·출시**

- `/qa-plan`, `/smoke-check` — 기동과 크리티컬 패스. 스크린샷 감상이 아님.
- `/soak-test` — 장시간 플레이.
- `/prototype`, `/vertical-slice` — 세로 조각. 잼에서는 전체를 만들지 않기 위한 절단.
- `/playtest-report`, `/bug-report`.
- `/release-checklist`, `/changelog`.

짧은 프로토타입이면 `/brainstorm` → `/vertical-slice` → `/smoke-check`만으로도 충분합니다.
그 세 단계 사이에 승인 없는 구현을 끼우지 않습니다.

### 4. 웹·인디에서 스킬을 쓰는 방식

조합은 **사람이 잠근 Plan → 그 범위의 브라우저 구현 → 필요한 이미지만 생성 → 브라우저로 직접 플레이**입니다.
루프는 `구현 → 입력 → 일시정지 → 상태 관찰 → 조정`이고, 관찰용 훅을 남깁니다.
스크린샷만 보고 "되는 것 같다"고 끝내지 않습니다. 창작자가 플레이해 보고 거절할 수 있어야 합니다.

같이 켜 두는 것:

- **imagegen** — 컨셉, 스프라이트, 배경, UI. 프롬프트는 재사용할 수 있게 파일로 남김. 아트 바이블 밖 이미지는 받지 않음.
- **develop-web-game** — 로컬 서버의 게임을 실제로 조작해 검증.
- **플레이 검증** — 타이밍, 히트감, HUD. 느낌의 최종 판단은 사람.

웹 인디에서 자주 만드는 커스텀 명령:

| 명령 | 하는 일 |
| --- | --- |
| `/loop` | 입력→판정→보상→재시작만. 메타, 스토리, 상점 금지 |
| `/feel` | 히트스톱, 카메라 쉐이크, 화면 플래시, SFX 훅만 조정 |
| `/sprite` | 아트 바이블 규격으로 시트 생성 후 피벗·프레임 검증 |
| `/balance` | 지정 시뮬 N회, 클리어율·평균 시간만 보고 |
| `/mobile` | 터치 타깃, 세이프 에어리어, 60fps 예산 |
| `/itch` | 빌드, 스크린샷, 설명문, 조작 안내 |
| `/jam` | 짧은 스코프. 기능 상한, 아웃 오브 스코프 명시 |

엔진에 연결하더라도, 씬을 읽고 제안하게 한 다음 창작자가 `/vertical-slice`의 경계를 넘깁니다.
엔진 코드를 채팅창에 붙여 넣고 통째로 다시 쓰게 하는 방식은 제어를 잃는 지름길입니다.

### 5. 실제로 치는 순서

**새 프로토타입 (웹, 하루~이틀)**

1. `/init` — 스택, 해상도, "싱글 파일 또는 src/ 3개 이하", 만들지 말 것.
2. `/plan` — 코어 루프 한 문장, 화면 3개, 안 만들 것. 승인 전에는 구현 없음.
3. 계획을 `PLAN.md`로 저장.
4. 이미지 생성은 플레이어·적·타일만. 바이블 밖은 버림.
5. `/goal` — "로컬에서 시작 버튼을 누르면 30초 생존 후 게임오버가 뜨고, 콘솔 에러 0, 40턴에서 중단".
6. `/review`로 창작자가 닫고 → `/compact`.

**이미 있는 빌드에 기능 하나**

1. `/plan 대시 추가. 쿨다운 0.8초, 무적 없음, 모바일 스와이프. 다른 이동기는 금지`.
2. 스토리 하나. 수용 기준이 없으면 구현하지 않음.
3. `/goal` — 대시 중 충돌이 기존 히트 판정과 이중으로 안 들어가고, 기존 웨이브 테스트가 통과.
4. `/balance-check` 또는 `/feel`. 숫자와 타격감은 따로 봄.
5. 창작자가 `/story-done`.

**막힐 때**

- 범위가 새면 `/scope-check`. 새 기능을 보태지 않음.
- 손이 안 맞으면 `/feel`만 분리. 로직 리팩터와 섞지 않음.
- 컨텍스트가 꼬이면 `/compact` 후 `/clear`, `PLAN.md`만 다시 읽힘.
- 실험이 실패하면 `/rewind` 또는 `/fork`. 실패한 생성을 본류에 남기지 않음.

### 6. `/goal`을 창작 주권 안에서 쓰는 조건

1. Brief — 한두 문장. 창작자가 쓴 문장.
2. Stack — 엔진, 라이브러리, 스킬.
3. Scope — 비주얼 / 기능.
4. Out of Scope — 이게 없으면 루프가 상점을 만들기 시작합니다.
5. Constraints — 유지할 것(기존 입력, 60fps, 파일 수).
6. Definition of Done — 검증 문장 하나.
7. Acceptance — 5~10개 하위 체크. 창작자가 하나씩 수락하거나 거절.
8. Verification — 매 턴 돌릴 명령 또는 눈으로 볼 조건.
9. Turn Budget — 상한. 없으면 토큰만 타고, 슬롭만 쌓임.

나쁜 예: `/goal 재밌는 로그라이크 완성`.
나은 예: `/goal npm run dev 후 3웨이브 클리어, 게임오버에서 재시작, 콘솔 에러 0, 25턴에서 중단`.

명령 이름을 외우기보다, **계획(`/plan`)과 종료 조건(`/goal`)을 코드보다 먼저 파일로 남기는 것**이 이번 주제입니다.
그 파일의 저자는 에이전트가 아니라 창작자입니다.
스킬은 그 다음, 반복되는 손만 `/` 하나로 줄이는 용도입니다.
