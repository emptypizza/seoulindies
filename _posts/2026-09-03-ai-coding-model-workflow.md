코드의 대부분은 에이전트에게 맡길 수 있습니다.
사람이 남는 일은 두 가지입니다.
에이전트가 일할 환경을 고정하는 것, 그리고 나온 코드를 가끔 읽는 것.

모델을 바꿔 본 뒤의 감과, 그다음 작업 순서를 적습니다.

## 모델

**Claude.** 무난합니다. 시킨 일의 결을 잘 맞춥니다. 디버깅에서는 헛소리를 할 때가 있어, 버그 추적은 따로 봐야 합니다. 가벼운 요금제는 금방 바닥납니다.

**GPT, Codex.** 시킨 범위 안에 머무르고, 꼼꼼합니다. 프롬프트를 잘게 쓰는 사람에게 맞습니다. 많이 돌리면 주간 한도를 금방 채웁니다.

**Gemini.** 코딩보다 시나리오와 글에 가깝습니다. 코딩 주력으로 두기는 아쉽습니다.

**Grok.** 체급은 Claude나 GPT보다 낮게 느껴집니다. 작업이 어렵지 않으면 쓸 만합니다. 긴 컨텍스트와 장기 코딩에서는 사용량이 빨리 줄어듭니다. 하네스를 먼저 고정해야 합니다.

시작할 때는 Claude를 권합니다. 특히 비전공이라면, 알잘딱이 먼저입니다.

## 워크플로

설계를 먼저 합니다.
대화로 컨텍스트를 쌓고, 인터뷰형 질문으로 의도를 맞춥니다.
문서가 의도를 담았는지 본 뒤에야 구현으로 갑니다.
바로 코드를 열지 않습니다. 이슈를 먼저 등록합니다.

GitHub Issue와 Pull Request로 일감과 마일스톤을 둡니다.
새 기능과 버그는 이슈입니다.
작업 중 발견한 버그는 별도 이슈로 미룹니다.
PR 전에는 AI 리뷰를 돌리고, 지적은 한 이슈에 묶거나 나눕니다.

이슈 문장은 에이전트가 써도 됩니다.
다음 작업은 이슈 번호로 부릅니다.
에이전트가 그 이슈를 읽고 컨텍스트를 잡게 합니다.

메모장에만 있으면 전달이 안 됩니다.
일감이 파일로 있고, 에이전트가 그 파일에 닿을 수 있어야 합니다.
GitHub가 아니어도 됩니다. 그 두 조건이면 됩니다.
